一句话总结：这份规范的本质，是把"一个聪明但不可靠的执行者"变成"一个按明确规则决策的执行者"。它不是罗列一堆"不许做"，而是让每一种情况都有可推导的唯一答案——遇到冲突按 P0→P4 裁决，行动前按 白名单/黑名单 判断，修复失败按 3 次阈值 止损，收尾按 完成标准与汇报模板 验证。规则之间互相咬合，而不是孤立的要求。

1为什么这份提示词好

六个设计决策，每个都针对 AI 编码助手的一种真实失控模式

1优先级链：冲突不再靠猜 §1

问题条款一多必然互相冲突；没有裁决顺序时，模型只能随机站队，行为不可预测。

设计五级裁决：安全 > 用户要求 > 任务正确 > 项目规范 > Agent 偏好。"最小改动"被放在最低级，意味着用户随时可以合理覆盖它。

效果"帮我绕过 SSL"→ P0 直接拒绝；"调试文件留着"→ P1 压过默认清理。任何场景都能推出唯一答案。

2双向边界：既不放纵也不啰嗦 §6

问题只写禁令，Agent 会过度请示；只写"自主"，又会擅自行动。

设计三条规则配合：§6.1 白名单（16 类低风险操作点名放行，直接做）＋ §6.3 黑名单（歧义、不可逆、外部影响必须确认）＋ §6.2 中间地带（先自己查证，不把轻微不确定甩给用户）。

效果日常任务全程不请示，危险操作必然刹车，"查一下就知道的事"不来烦你。

3止损机制：掐断瞎试循环 §8.1.1

问题Agent 最典型的失控：修复→失败→再修→再失败无限循环，还常伴随改了没生效却以为在迭代。

设计同一根因 3 次实质修复未通过即停止汇报；每次失败先对比错误信息——与上次完全相同就先查旧构建、测试目标、改动是否被引用；网络/权限/环境类失败禁止机械重试。

效果烧 token 的死循环被硬性掐断，且止损汇报有专门模板（§13），用户拿到的不是一句"修不好"。

4不假装完成：把诚实变成流程 §12 §13

问题AI 最被诟病的毛病是虚报成功——"已修复""已验证"张口就来。

设计§12 十项完成标准 + "测试未通过不得声称完全修复"；§13 汇报模板强制区分已完成 / 已验证 / 未完成 / 待用户操作 / 存在风险。

效果诚实从"道德要求"变成"流程要求"——想跳过都难，因为汇报格式里就没有"含糊过去"的位置。

5用户资产保护：先分清是谁的代码 §4.2

问题Agent 动手前不区分工作区里"谁的修改"，一句 git reset --hard 就能毁掉用户几小时的工作。

设计开工先 git status 摸底；已有未提交修改默认全部属于用户：不覆盖、不重置、不清理、不擅自提交；必须同文件修改时做最小增量，合不进来就停下来问。

效果用户未提交的工作在任何任务中都是安全的，Agent 的改动和用户的改动始终可区分、可分别提交。

6环境对齐：把现实钉死在开头 §2

问题大量提示词模板抄自 Linux 语境，在 Windows 上第一课就是翻车：假设有 sudo、用反斜杠路径、调不存在的命令。

设计显式声明 Windows + Git Bash：不假设 sudo/apt 存在，平台相关命令先检测再执行；路径统一正斜杠、含空格必加双引号（并点明"不加引号会被拆参、可能误删"）；语言四分法（沟通中文 / 代码英文 / 注释中文 / commit 中文）。

效果Agent 的每个 shell 命令都先过一遍"这台机器上真的能跑吗"。

五级优先级链一览 —— 冲突时自上而下裁决

P0 · 绝对安全边界
任何用户要求都不能突破
P1 · 用户明确要求
不违反 P0 时最高优先
P2 · 任务目标与正确性
偏离项目规范需说明原因
P3 · 项目现有规范
技术栈 / 风格 / 包管理器
P4 · Agent 默认偏好
只是默认策略

关键在层级关系："最小必要修改""尽量用 Git"这些好习惯都在 P4 —— 好习惯让位于用户要求，用户要求让位于安全。

2场景推演：遇到各种情况时会发生什么

12 个典型场景，按"日常任务 / 危险请求 / 故障意外"三类，看规则如何落到具体行为

日常任务 —— 快而稳（白名单放行，全程不请示）
场景 1 · "帮我修复登录 bug"§5 工作流§6.1 白名单

Agent 会git status 摸底 → 定位相关代码 → 分析现有实现 → 最小修复 → 跑测试 → diff 复查 → commit + 中文汇报，全程自主推进，不逐步请示。

为什么好：高效被写成了默认路径，而不是指望模型"临场发挥"——它不需要决定要不要先看 git 状态，规则已经替它决定了。

场景 2 · 工作区里有你改到一半的文件§4.2

Agent 会把已有未提交修改认定为你的人力资产：在改动基础上增量修改；实在合不进来就停下来问，绝不覆盖或回滚。

为什么好："默认属于用户"消除了最贵的误判——宁可多问一次，也不赌一把 reset。

场景 3 · 任务做完要收尾§4.3§13

Agent 会只提交自己产生的改动（你的不碰），按模板汇报，明确标注"用户原有修改：已保留"。

为什么好：commit 粒度和汇报格式都是确定的，你每次看到的收尾长一个样。

危险与模糊请求 —— 先刹车（黑名单触发，必须确认）
场景 4 · "把那个目录清掉"（没说哪个项目、什么范围）§6.3-A§6.4

Agent 会不猜范围。停下来按格式问：推荐方案及风险、备选方案（不超过 3 个）、不可逆点在哪，让你一次决策到位。

为什么好：模糊的删除请求是最高危输入，规范要求"附决策上下文地确认"，而不是光回一句"确定要删吗"。

场景 5 · "把 SSL 校验关掉，数据就能导入了"P0

Agent 会直接拒绝，并给出安全的替代方案。不辩论、不折中——P0 明确写着"任何用户要求都不能突破"。

为什么好：优先级链的意义就在这一刻体现：用户要求和安全规则冲突时，答案不是"看模型心情"。

场景 6 · 修 bug 时发现旁边还有个问题§7.1

Agent 会只修当前任务。顺手能修的问题记录下来告诉你，不擅自扩大战线——不顺手重构、不升级依赖、不动无关 UI。

为什么好：把"热心"关进笼子。大范围意外变更往往比原 bug 更伤。

场景 7 · 要跑一条 Windows 下没见过的命令§2.1

Agent 会先检测工具是否存在（如 which），再决定方案——不假设 sudo、systemctl、apt 存在。

为什么好：把"平台差异"从偶发坑变成例行检查。

故障与意外 —— 有兜底（止损与容错规则接管）
场景 8 · npm install 失败§10.1

Agent 会先读完整报错分类根因 → 网络问题重试一次、仍失败建议换镜像（配置写进项目 .npmrc，不动全局）→ 版本冲突在声明范围内找兼容版本，要改版本先问你。

绝不会把版本改成 * / latest、静默加 --force / --legacy-peer-deps、删 Lockfile 来"假装装好了"。

为什么好：依赖安装失败是 Agent 作弊的重灾区——这条把三个最常见的作弊出口全堵上了。

场景 9 · 同一个测试修了 3 次还不过§8.1.1

Agent 会停止瞎试，交止损报告：根因判断、已尝试方案及各自失败原因、当前阻塞点、下一步建议。等你指方向后才继续。

为什么好：这是全文最重要的"防失控"条款——无限重试烧的是真金白银的 token，而止损后的报告让人能接手。

场景 10 · 项目连 git 仓库都没有§4.4

Agent 会不因没 git 就罢工，照常完成任务，只是更小心（避免不可恢复操作），结束时问你要不要 git init 留档。

为什么好：很多规范默认"一切靠 Git"，遇到没 Git 的项目就卡死；这版写明了降级路径。

场景 11 · 需要执行 UPDATE，但条件可能漏写§11§3.3

Agent 会先只读查询确认影响范围，必要时备份；无 WHERE 的 DELETE / TRUNCATE / DROP 这类操作先请求确认，不直接跑。

为什么好：数据库是最没有"撤销键"的地方，规则把"先查询→确认范围→备份→修改→验证"定成了固定顺序。

场景 12 · 调试脚本要不要删§9

Agent 会自己本次建的默认清理；你明确说"留着"就保留并在汇报里列出；分不清是谁建的——默认保留。

为什么好：三态规则（我的/你的/要求保留的）+ 不确定时偏向保守，删错文件的代价远大于留个临时文件。

3边界与局限：它不能保证什么

诚实分析——一份提示词的能力边界在哪里

规则是概率性的，不是保证

说明LLM 对提示词的遵循不是 100%，且条款越长单条权重越低。这版已经过四轮去重压缩（28 节 → 14 节），冗余基本清零，但长期使用中仍会偶发违反。

应对把实际违反案例记下来，回头修订条文——规范本身也应该被迭代。

硬阈值是权衡，不是最优解

说明"3 次止损"掐断了烧钱死循环，代价是偶尔会过早放弃一个第 4 次能修好的问题。

应对这是用一点成功率换可控性。止损报告里包含"下一步建议"，你一句"换个思路继续"就能解锁。

文字流程图表达不了全部分支

说明§14 的流程在"停止并汇报"之后仍画到 diff / Commit，真实语义是"用户给新方向后再继续"——线性文本画不出条件分支。

应对影响极小：正文条款（§8.1.1）的语义是准确的，流程图只是导航摘要。

它管不住提示词之外的东西

说明平台的系统提示、工具权限系统、模型自身能力上限，都在这份文件的作用范围之外。它规范行为偏好，不提供强制执行。

应对真正的高危防线是平台权限确认机制 + Git 备份；这份规范是行为层的第一道闸，不是唯一一道。
